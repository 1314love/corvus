## What is in the tree

The tree declares 62 MCP tools in ten categories and adds 18 tools; the page category grows from 11 to 15. It adds no crate or REST route and keeps the recording schema unchanged, but the extension permission count rises from 10 to 11 with `tabGroups`. Every screenshot and PDF is finalized once by the shared daemon dispatch path, and neither file is stored inline in a session step.

| `format` | `webp` (default), `png` or `jpeg` |

| `tab_id` | optional tab selector; the active tab is used when omitted |

## Capture targets and formats

`viewport` uses `Page.captureScreenshot` without capturing beyond the viewport. `full_page` reads the CSS content size from layout metrics and captures the full scrollable page. `element` resolves the reference to a box and captures that box; a `bbox` is returned only for an element capture. The extension uses its existing debugger channel and can fall back to `chrome.tabs.captureVisibleTab` only for an active-tab PNG viewport.

`format` selects the encoder and `mime_type`. `quality` is sent for webp and jpeg and omitted for png. Element references are channel-specific: CDP accepts `@cN` from `page_snapshot`, while the extension accepts `@eN`; passing the other kind returns `BAD_ARGS` before capture.

## page_pdf contract

`page_pdf` prints the selected or active tab with `paper_width` default 8.5 inches, `paper_height` default 11, `landscape` default false, `print_background` default true and `scale` from 0.1 to 2, with fixed 0.4-inch margins. The daemon decodes the PDF, enforces a 32 MiB (33,554,432-byte) decoded cap and writes a unique `page-<unix_millis>-<uuid8>.pdf` under `<daemon home>/pdf` with create-new semantics.

The result carries `format: "pdf"`, `mime_type: "application/pdf"`, `tab_id`, `url`, `path`, `bytes`, `sha256`, the paper fields and `summary`; it has no base64 field. `page_pdf` is excluded from `browser_batch`, and replay skips it with `page_pdf_not_replayable`.

## Screenshot storage and envelope

The daemon caps decoded image bytes at 8 MiB, rejects obviously oversized encoded payloads before decoding, verifies the dimensions, and writes `screenshot-<unix-millis>-<uuid8>.<ext>` under `<home>/screenshots/` without overwriting an existing file. The result returns `width`, `height`, `bytes`, `sha256`, `path`, `summary` and `inline` instead of base64.

A normal screenshot result is one compact JSON text block. With `inline: true`, the MCP envelope appends a second image content block and omits `structuredContent`. `browser_batch` rejects `inline: true` with `BAD_ARGS`; a step with `inline: false` is saved and finalized exactly once through the shared dispatch path. Recording strips `data` and `image.data` for screenshots and PDFs, and replay skips screenshots with `screenshot_not_replayable`.

## Channels and extension

CDP serves 46 browser-facing tools, the extension serves 42 and 12 are daemon-local. The four tab and window tools (`tab_group`, `tab_duplicate`, `window_list`, `window_new`) are extension-only, and forced CDP returns `CAPABILITY_UNAVAILABLE`. The extension declares 11 permissions including `tabGroups`, runs 42 debugger-based handlers and keeps `all_frames: false`; `health` and `version` are daemon-local only.

Under `auto`, CDP is preferred when connected and the extension is used only for an Unsupported route. `@cN` references are CDP-only and `@eN` references are extension-only; the wrong kind is `BAD_ARGS`. The daemon records the new tools like any other call, while the recording schema and its redaction rules stay at the same schema version.

## Architecture

`crates/corvus-mcp/src/tools.rs` declares 62 specs in ten categories; `crates/corvus-application/src/spec.rs` grows from 33 to 49 browser-side specs; `crates/corvus-cdp/src/tools.rs` lists 46 CDP browser-facing tools. The daemon adds `page_pdf`, `page_links`, `page_forms`, `page_accessibility`, `browser_drag`, `browser_focus`, `browser_highlight`, the four tab/window tools, the five storage tools and `health`/`version` dispatch.

The ten crates are unchanged. There is no new crate and no REST route change. `finalize_screenshot_result` and `finalize_page_pdf_result` run from the shared dispatch path, so a top-level call, an extension call and a `browser_batch` step are finalized exactly once.

## Guardrails and redaction

`browser_screenshot`, `page_pdf`, `page_links`, `page_forms`, `page_accessibility`, `window_list`, `storage_get`, `browser_highlight`, `health` and `version` are read-only for guardrails. `cookie_set`, `cookie_clear`, `storage_set`, `storage_clear`, `browser_drag`, `browser_focus`, `tab_group`, `tab_duplicate` and `window_new` are not read-only.

Recording redacts `cookie_set.value` and every `storage_set` entry value; guardrails replace every `storage_get` entry value with `[redacted]` and add `redacted: true`. Screenshot pixels and PDF bytes are not inspected, redacted or boundary-wrapped, so `deny_tools` is the way to block them. `browser_batch` excludes ten tools by name and leaves 42 batchable tools; `storage`, `sessions` and `help` are outside the batchable categories.
