# Corvus 1.2.0

Release date: 2026-11-15.

Corvus is a local Rust daemon plus a Manifest V3 browser extension. It exposes the browser that the user already runs to MCP clients over stdio or streamable HTTP. 1.2.0 is the hybrid transport release: the MCP surface grows from 32 to 42 tools, and the daemon can optionally drive a browser launched with remote debugging over a loopback browser-level CDP connection, while the extension remains the zero-setup default.

## What ships

- The original 32 MCP tools with unchanged arguments and result shapes, plus ten CDP and helper tools.
- A direct browser-level CDP client: one long-lived WebSocket, flattened Target sessions, a 1000-event ring, reconnect with 250 ms to 10 s backoff, a 15 s heartbeat and a 10 s default / 60 s maximum command timeout.
- Channel selection at startup and at runtime: `auto`, `cdp` and `extension`. `auto` prefers CDP and falls back only when the route is Unsupported; `cdp` is strict with no fallback; `extension` ignores CDP.
- Extension CDP detection on loopback ports 9222, 9223 and 9333 with same-browser-family selection; the endpoint is stored under `corvus.cdpEndpoint`.
- Two-level tool categories in `tools/list` and a brief default / full detail switch. `tool_help` returns the full descriptor.
- The single-root layout, Windows installer, Linux x86_64 package, Docker image and Kubernetes manifests introduced in 1.1.0. The release gates now expect 1.2.0 and 42 tools.
- An extension options page that stores the daemon URL and the optional CDP endpoint.

## Channel matrix

| Mode | Transport | Fallback | Notes |
| --- | --- | --- | --- |
| `auto` (default) | CDP when connected, otherwise the extension | Only when the CDP route is Unsupported | Stays on the extension when no endpoint is configured |
| `cdp` | Direct browser-level CDP only | None | Extension-only tools fail instead of silently changing channel |
| `extension` | Extension only | None | A configured CDP endpoint is ignored |

Select the mode with `--channel`, `CORVUS_CHANNEL` or the `browser_channel` tool. `--cdp-endpoint` takes the full loopback `ws://` or `wss://` browser URL from `/json/version`; `--no-cdp` removes the CDP path. The extension options page accepts `auto` or an explicit `http://127.0.0.1:<port>` discovery endpoint.

CDP is host-loopback only and unauthenticated. A browser-level endpoint can control every profile in that browser instance; never expose 9222, 9223 or 9333. See [07-cdp.md](../07-cdp.md) for launch flags, tool schemas, event handling and troubleshooting.

## Install

### Windows

The release ZIP contains `install-windows.ps1`, `uninstall-windows.ps1` and the vendored `nssm.exe`. Open an elevated PowerShell in the extracted archive and run:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\install-windows.ps1
```

The default root is `%ProgramData%\Corvus`; load the unpacked extension from `%ProgramData%\Corvus\extension`. A legacy `%USERPROFILE%\.corvus` tree is moved under the new root unless `-KeepLegacyData` is set. See [04-install.md](../04-install.md).

### Linux x86_64

```bash
mkdir -p corvus-1.2.0-linux-x86_64
tar -xzf corvus-1.2.0-linux-x86_64.tar.gz -C corvus-1.2.0-linux-x86_64
cd corvus-1.2.0-linux-x86_64
sha256sum -c SHA256SUMS
sudo ./install-linux.sh
```

The installer needs root and a running systemd. It creates the `corvus` service user, installs under `/opt/corvus`, writes and starts the unit, and waits for `http://127.0.0.1:7331/health`. Load the extension from `/opt/corvus/extension`. See [05-deployment.md](../05-deployment.md).

### Docker

```bash
docker volume create corvus-data
docker build -t corvus:1.2.0 .
docker run -d --name corvus \
  -p 127.0.0.1:7330:7330 -p 127.0.0.1:7331:7331 \
  -v corvus-data:/data corvus:1.2.0
curl -fsS http://127.0.0.1:7331/health
```

The image runs as UID/GID 10001 with `/data` as its home and carries the extension at `/opt/corvus/extension`. It contains no browser and cannot reach browser loopback on the host, so use the extension channel or `--no-cdp` inside the container.

### Kubernetes

```bash
docker build -t corvus:1.2.0 .
kind load docker-image corvus:1.2.0   # or push to your registry
kubectl apply -k deploy/k8s
kubectl -n corvus port-forward svc/corvus 7330:7330 7331:7331
```

The Service is a ClusterIP. A browser extension cannot reach it directly; use the port-forward or an authenticated proxy that the operator provides. CDP is not reachable from a pod by default. See [deploy/k8s/README.md](../../deploy/k8s/README.md).

## Verify

```bash
curl -fsS http://127.0.0.1:7331/health     # status ok, version 1.2.0
curl -fsS http://127.0.0.1:7331/metrics   # Prometheus text
corvus doctor
```

An MCP `tools/list` request returns exactly 42 tools. Call `browser_channel` with no arguments to read the active mode, CDP connection and extension state, and `cdp_status` for the endpoint, browser, protocol version, target count, reconnect count and last error. When CDP is expected but absent, check the launch port and the extension detection state before changing the channel.

## Known limitations

- NFR-3 is not passed. The clean 72-hour soak was stopped at the client's request after about eight hours, and 1.2.0 is not 72-hour soak certified.
- Firefox remains unsupported (NFR-6 deviation unchanged). Supported browsers are Edge, Chrome and Brave (Chromium 120+).
- CDP is loopback-only and unauthenticated, and a browser-level endpoint can control every profile in that browser instance. Never expose 9222, 9223 or 9333.
- The shipped Docker image and Kubernetes manifests contain no browser and cannot reach browser loopback on the host. A sidecar browser is not supported out of the box; use the extension channel or `--no-cdp`.
- Forced `cdp` never falls back, so extension-only tools require the extension and a shared tool may fail when the CDP route is unavailable.
- macOS has no packaged installer; Linux packaging is x86_64 only. The image is not published to a registry, and Kubernetes manifests are release-gate checks rather than a hosted deployment.
- No live 1.2.0 deployment is claimed. The development machine used for packaging continued to run the existing 1.0.0 service.
- Extension tab ids and CDP target ids are different namespaces. v1.2.0 returns typed `BAD_ARGS` hints and extension-only tools work without `tab_id`; full bridging is deferred to v1.3.
- An explicitly configured extension CDP endpoint changed while the daemon is already connected may require a daemon restart to take effect. Auto-discovered endpoint changes are re-polled and reconnect automatically (reconnect verified).

## Upgrade from 1.1.0

The recording schema remains version 1, so a 1.1.0 database opens in place; no migration is required.

- Windows: run the 1.2.0 installer with the same `-HomeDir`. The installer refreshes binaries and the extension and keeps `data/corvus.db`.
- Linux: replace the installed tree with the 1.2.0 archive and rerun `install-linux.sh`; keep `<root>/data` and `<root>/config`.
- Docker: rebuild or pull the 1.2.0 image and keep the named `/data` volume. Kubernetes: update the image tag in the deployment.
- Reload the extension after replacing its files. Existing daemon URL settings are kept; the CDP endpoint stays optional. Run `corvus doctor`, check `/health`, and call `tools/list` to confirm 42 tools.

See [Upgrade in the install guide](../04-install.md) and [05-deployment.md](../05-deployment.md).
