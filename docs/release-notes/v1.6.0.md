## What is in the release

The tree adds an optional local guardrails policy enforced by the daemon, a localized extension error for policy denials, and no new MCP tool. The catalogue remains 43 tools in nine categories. Nothing in this section has been published as a 1.6.0 release.

## Guardrails policy

The policy file is strict JSON, at most 65,536 bytes, with required `version: 1` and the optional fields `read_only`, `allow_tools`, `deny_tools`, `allowed_hosts`, `block_private_network`, `redact_secrets` and `content_boundary`. Unknown fields, unknown tool names, allow/deny overlap and invalid host patterns are fatal at startup. See [11-guardrails.md](../11-guardrails.md) for the schema, host-pattern grammar and three worked examples.

Tool checks run read-only first, then the allow list, then the deny list. The URL gate checks `browser_navigate` and `tab_new` arguments before dispatch and re-checks the returned URL for `browser_navigate`, `tab_new` and `browser_history`. `about:blank` is always allowed; `allowed_hosts` requires http or https and rejects suffix tricks; private-network blocking is literal and never resolves DNS.

Enable it with `--guardrails <PATH>` or `CORVUS_GUARDRAILS=<PATH>`. An invalid policy aborts daemon startup with an invalid-input error; the policy body is never logged.

## Enforcement and error surface

`RouterBackend::call` in `crates/corvusd/src/lib.rs` checks the tool policy and navigation arguments before dispatch. A denied call is recorded and returns an error without reaching the browser. The gate is daemon-side; the extension does not evaluate the policy.

`browser_batch` checks each step and stops on the first denial by default; a batch cannot bypass the policy for a nested step. `session_replay` checks each planned or live step and records a denied step as skipped with reason `policy_denied`.

A denial is the 11th error code, `POLICY_DENIED`, with `retryable: false`. Tool denials use `tool <name> denied by guardrails policy (<reason>)`; URL denials use `navigation denied by guardrails policy (<reason>)`. Details carry the reason and the policy source path.

REST returns HTTP 403 with the error body nested under `error`. A post-dispatch URL denial still reports `POLICY_DENIED`, but the navigation has already happened.

## Secret redaction and content boundaries

With `redact_secrets`, every object in the top-level `cookies` array of a `browser_cookies` result that has a `value` field becomes `value: "[redacted]"` with `redacted: true`. Other tools, nested values, headers and page text are not redacted.

With `content_boundary`, `page_text` text, `page_html` html and compact `page_snapshot` text are wrapped in the exact Corvus untrusted-content markers. Embedded markers are escaped first, so the final value has exactly one leading and one trailing marker. JSON snapshots are untouched.

Password masking is independent of guardrails: snapshot password values render as `***`. `browser_type` differs by channel: the extension returns `masked: true` for password fields and a truncated `value` otherwise, while CDP omits `value` and does not emit `masked`, so no typed value is returned.

## Extension behavior

When the daemon returns `POLICY_DENIED`, the Vue UI shows the localized `errors.policyDenied` message, or `errors.policyDeniedWithReason` with the sanitized reason. It never displays the policy source path and offers no retry action.

The extension change is presentational only. It does not parse, cache or enforce the guardrails policy locally, and it does not add a new permission or handler.

## Tool surface

The MCP catalogue is unchanged: 43 tools in nine categories. This work adds no tool, removes no tool and changes no tool input for guardrails; policy denials are returned through the existing error envelope.

## Architecture

The ten crates are unchanged: `corvus-domain`, `corvus-application`, `corvus-api`, `corvus-proto`, `corvus-mcp`, `corvus-transport`, `corvus-record`, `corvus-cdp`, `corvusd` and `corvus`. Guardrails live in the daemon, not in a new crate.

`crates/corvusd/src/guardrails.rs` owns the policy model, parsing, host matching, URL checks, redaction and boundary wrapping. `RouterBackend::call`, `run_batch` and `session_replay` are the enforcement points in `crates/corvusd/src/lib.rs`.

There is no new crate, no REST route change and no recording schema change. The guardrails module is opt-in and leaves the 1.5.0 architecture intact when no policy is configured.

## Deployment and health

Operators pass `--guardrails` or set `CORVUS_GUARDRAILS`. The daemon rejects an unreadable, oversized, malformed, unknown-field, wrong-version, unknown-tool, overlapping or invalid-pattern policy before serving traffic. See [05-deployment.md](../05-deployment.md).

`/health` exposes `health.guardrails` with `enabled`, `read_only`, `allow_tools`, `deny_tools`, `allowed_hosts`, `block_private_network`, `redact_secrets` and `content_boundary`; list fields are counts, never names. REST `/api/v1/health` returns the same object.

## Known limits

- The navigation gate is not a network sandbox. After an allowed load, page scripts can still fetch denied origins, and subresources are not filtered by `allowed_hosts`.
- DNS is never resolved. A hostname that passes the pattern can resolve to a private address, and DNS rebinding is not detected.
- `browser_eval`, `page_html` and `browser_history` can expose secrets; redaction covers only the cookie values described above, and pasted HTML attributes are not scrubbed.
- JSON snapshots are not boundary-wrapped; only compact snapshot text, `page_text` text and `page_html` html are.
- `browser_type` result shape differs by channel: the extension returns `masked: true` for password fields and a truncated `value` otherwise; CDP omits `value` and does not emit `masked`.
- The 1.6.0 QA report records one Low finding for this per-channel `browser_type` result-shape difference and no High or Medium findings.
- REST auth accounts and refresh tokens are in memory; guardrails do not add persistent identity.
- A post-dispatch redirect denial reports `POLICY_DENIED` after the browser may already have followed the redirect.
- `details.policy` exposes the local policy path to direct MCP and REST clients; the extension UI hides it.
- No live 1.6.0 deployment is claimed, and NFR-3 remains unpassed. QA PASS was measured on the dirty working tree at HEAD `61ca85f`; no v1.6.0 tag, CI run, published package or published asset exists, so release evidence remains Pending. The distinct local installer ZIP passed local acceptance (84 checks and observations, 0 failures), but it is not a published release artifact.
