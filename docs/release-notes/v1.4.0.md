# Corvus 1.4.0

Release date: 2026-11-15. This note describes the 1.4.0 release. The v1.4.0 acceptance report records PASS at HEAD 65fbf52; CI run identifiers and the GitHub Release remain pending.

Corvus is a local Rust daemon plus a Manifest V3 browser extension. It exposes the browser that the user already runs to MCP clients over stdio or streamable HTTP. 1.4.0 is a structural release: the backend moves to ports and adapters, a REST `/api/v1` surface joins MCP, recording moves to SeaORM migrations, and the extension is rebuilt from TypeScript and Vue 3 sources. The MCP surface itself is unchanged at 43 tools, with the compact single-text result envelope and `browser_batch` exactly as in 1.3.0.

## What ships

- `corvus-domain` for the pure domain model and `corvus-application` for use cases plus the `BrowserRegistry`, `BrowserSession`, `StepRecorder` and `ToolCatalog` ports. `corvus-cdp`, `corvus-transport`, `corvus-record`, `corvus-mcp` and `corvus-api` are adapters; `corvusd` composes them. `corvus-runtime` is removed.
- REST on `/api/v1`: health, browsers, sessions, tools and authentication. OpenAPI JSON is at `/api-docs/openapi.json` and Swagger UI at `/docs`. REST shares the 43-tool catalogue and executor with MCP.
- Optional local authentication with Argon2id passwords, HS256 JWTs, 900-second access tokens and rotating 30-day refresh tokens. Auth is off by default on loopback, there is no default account, and a non-loopback bind without auth fails startup unless `--allow-no-auth` / `CORVUS_ALLOW_NO_AUTH` is set explicitly.
- SeaORM and `sea-orm-migration` recording with `schema_version` 1. Existing databases are opened without a data migration; a pre-migration `VACUUM INTO` backup is written and a failed backup aborts startup. The store keeps WAL, one writer connection, a 5-second busy timeout, 30-day retention and 262144-byte payload truncation.
- An extension rebuilt from TypeScript and Vue 3: Vue 3, Pinia and Naive UI for the popup and options page; framework-free TypeScript for the service worker, content script and offscreen document; typed RPC; three Vite builds to `extension/build/extension`; ten MV3 permissions; 21 unit, contract and component tests plus an isolated Playwright suite.
- The 1.1.0 single-root layout, Windows installer, Linux x86_64 package, Docker image and Kubernetes manifests, now labelled 1.4.0. The Docker image entrypoint passes `--allow-no-auth`; that is an explicit unsafe opt-out, not a turnkey secure container.

Select the mode with `--channel`, `CORVUS_CHANNEL` or the `browser_channel` tool. CDP remains host-loopback only and unauthenticated; see [07-cdp.md](../07-cdp.md).

## REST API and authentication

The daemon serves these routes on the same HTTP port as `/mcp`:

| Method | Path |
| --- | --- |
| GET | `/api/v1/health` |
| GET | `/api/v1/browsers` |
| GET | `/api/v1/browsers/{id}` |
| GET | `/api/v1/sessions` |
| GET | `/api/v1/sessions/{id}` |
| GET | `/api/v1/sessions/{id}/steps` |
| GET | `/api/v1/tools` |
| POST | `/api/v1/tools/call` |
| POST | `/api/v1/auth/login` |
| POST | `/api/v1/auth/refresh` |
| POST | `/api/v1/auth/logout` |
| GET | `/api/v1/auth/me` |

Authentication is controlled by `--auth off|local` / `CORVUS_AUTH`. `local` requires a signing secret of at least 32 bytes and bootstrap username and password; there are no default credentials. Access tokens last 900 seconds. Refresh tokens last 30 days, are stored as Argon2id hashes and rotate on use. Every response carries `x-request-id`; the router adds tracing, a 120-second timeout returning 408, gzip and CORS restricted to loopback origins.

The bearer guard covers `/api/v1` only, with `/api/v1/health`, login and refresh exempt. `/mcp`, the extension WebSocket, legacy `/health`, `/metrics`, `/api-docs/openapi.json` and `/docs` remain unauthenticated even when local auth is on. REST auth therefore does not make a non-loopback daemon remote-safe. Accounts and refresh tokens live in memory in 1.4.0 and do not survive a restart.

## Persistence and upgrade

The recording store keeps `schema_version` 1. A 1.3.0 database opens without a data migration and remains readable by a 1.3.0 binary. Before the baseline migration runs on an existing file, the daemon writes `VACUUM INTO <db>.backup-<millis>.db`; a failed backup aborts startup. One recorder task drains the write queue, reads run on a dedicated record thread, previously active sessions are marked `abandoned`, sessions older than 30 days are pruned, and stored arguments and results are truncated at 262144 bytes on a UTF-8 boundary.

## Extension build

Build and load the extension from the generated tree:

```bash
pnpm --dir extension install
pnpm --dir extension build
```

Load `extension/build/extension`. The build performs three Vite passes, copies the manifest last, validates the ten permissions and the module service worker, and rejects source maps. The popup and options page are Vue 3 applications; the service worker, content script and offscreen document stay framework-free TypeScript.

## Install

### Windows

The release ZIP contains `install-windows.ps1`, `uninstall-windows.ps1` and the vendored `nssm.exe`. Open an elevated PowerShell in the extracted archive and run:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\install-windows.ps1
```

The default root is `%ProgramData%\Corvus`; load the extension from `%ProgramData%\Corvus\extension`. A legacy `%USERPROFILE%\.corvus` tree is moved under the new root unless `-KeepLegacyData` is set. See [04-install.md](../04-install.md).

### Linux x86_64

```bash
mkdir -p corvus-1.4.0-linux-x86_64
tar -xzf corvus-1.4.0-linux-x86_64.tar.gz -C corvus-1.4.0-linux-x86_64
cd corvus-1.4.0-linux-x86_64
sha256sum -c SHA256SUMS
sudo ./install-linux.sh
```

The installer needs root and a running systemd. It creates the `corvus` service user, installs under `/opt/corvus`, starts the unit and waits for `http://127.0.0.1:7331/health`. See [05-deployment.md](../05-deployment.md).

### Docker

```bash
docker volume create corvus-data
docker build -t corvus:1.4.0 .
docker run -d --name corvus \
  -p 127.0.0.1:7330:7330 -p 127.0.0.1:7331:7331 \
  -v corvus-data:/data corvus:1.4.0
curl -fsS http://127.0.0.1:7331/health
```

The image runs as UID/GID 10001 with `/data` as its home and carries the extension at `/opt/corvus/extension`. Its entrypoint passes `--allow-no-auth`, so the container is explicitly unauthenticated and is not turnkey secure; publish only to host loopback. To enable REST auth, pass the four `CORVUS_AUTH*` variables with `--env-file`. The image contains no browser and cannot reach browser loopback on the host.

### Kubernetes

The manifests in `deploy/k8s/` create the namespace, PVC, daemon Deployment, ClusterIP Service and NetworkPolicy. The checked-in Deployment overrides the image entrypoint and passes `--allow-no-auth`, so the pod starts but is explicitly unauthenticated and not turnkey secure. MCP, the extension WebSocket, `/health`, `/metrics`, `/api-docs/openapi.json` and `/docs` remain unauthenticated. CDP is not reachable from a pod by default. See [deploy/k8s/README.md](../../deploy/k8s/README.md).

## Known limitations

- REST auth accounts and refresh tokens are in memory in 1.4.0 and reset on restart. Persistent auth storage is future work.
- The bearer guard covers `/api/v1` only. `/mcp`, the extension WebSocket, legacy `/health`, `/metrics`, `/api-docs/openapi.json` and `/docs` are unauthenticated even when local auth is on. Use a trusted authenticating proxy for any non-loopback listener.
- The checked-in Kubernetes Deployment overrides the image entrypoint and passes `--allow-no-auth`. The pod starts, but the deployment is explicitly unauthenticated and MCP remains unauthenticated; the opt-out does not protect it.
- NFR-3 is not passed. The planned 72-hour soak remains incomplete after the earlier stop at about eight hours; 1.4.0 is not soak certified.
- Firefox remains unsupported (NFR-6 deviation unchanged). Supported browsers are Edge, Chrome and Brave (Chromium 120+).
- CDP is loopback-only and unauthenticated, and the shipped Docker image and Kubernetes manifests contain no browser and cannot reach browser loopback on the host.
- Forced `cdp` has no fallback; macOS has no packaged installer; Linux packaging is x86_64 only.
- During the first packaging check, the browser launch briefly attached CDP to the user's Edge instance on port 9222 without an MCP or REST call or any navigation; it was stopped and rerun isolated.
- Extension tab ids and CDP target ids remain separate namespaces; cross-channel references return typed `BAD_ARGS`.
- No live 1.4.0 deployment is claimed. The development machine continues to run the existing 1.0.0 service.

## Upgrade from 1.3.0

`schema_version` remains 1, so a 1.3.0 database opens in place. Before the baseline migration runs on an existing file, the daemon writes a `VACUUM INTO` backup; a failed backup aborts startup.

- Windows: run the 1.4.0 installer with the same `-HomeDir`. It refreshes binaries and the extension and keeps `data/corvus.db`.
- Linux: replace the installed tree with the 1.4.0 archive and rerun `install-linux.sh`; keep `<root>/data` and `<root>/config`.
- Docker: rebuild or pull the 1.4.0 image and keep the named `/data` volume. Kubernetes: update the image tag; the checked-in Deployment already passes `--allow-no-auth`, which starts the pod but leaves it explicitly unauthenticated.
- Rebuild the extension from source or replace the packaged tree, then reload it. Existing daemon URL and CDP endpoint settings are kept. Run `corvus doctor`, check `/health` and `/api/v1/health`, and call `tools/list` to confirm 43 tools.

See [Upgrade in the install guide](../04-install.md) and [05-deployment.md](../05-deployment.md).
