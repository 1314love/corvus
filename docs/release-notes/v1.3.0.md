# Corvus 1.3.0

Release date: 2026-11-15.

Corvus is a local Rust daemon plus a Manifest V3 browser extension. It exposes the browser that the user already runs to MCP clients over stdio or streamable HTTP. 1.3.0 is the token-efficiency release: the MCP surface grows from 42 to 43 tools, `page_snapshot` defaults to a compact text format on both channels, tool discovery is lean by default, and forced CDP now serves every browser-facing tool. The original 32 result shapes remain unchanged.

## What ships

- `browser_batch`: up to 20 allowlisted browser steps in one call, with `stop_on_error` default true and a per-step result array. It is daemon-local and is not sent to a browser channel.
- Compact `page_snapshot` on both extension and CDP: `format: "compact"` is the default, `format: "json"` returns the former node-object shape, and `viewport_only`, `include_bbox` and `max_nodes` are supported.
- Lean `tools/list`: brief is the default and removes titles plus schema property descriptions; `detail: "full"` restores them. `tool_help` returns one full descriptor or a category index.
- Full CDP parity for all 33 browser-facing tools. The eight former extension-only tools work under forced `cdp`, and `@c<backendNodeId>` references are available from CDP snapshots.
- Nine tool categories, 43 tools in total, and `_meta["corvus.category"]` on every definition.
- Logging follows one documented event schema, and startup emits a single `corvusd listening` event; see [08-logging.md](../08-logging.md).
- One compact JSON text block per successful `tools/call` and no `structuredContent`; clients parse `content[0].text`.
- The single-root layout, Windows installer, Linux x86_64 package, Docker image and Kubernetes manifests introduced in 1.1.0. Release assertions now expect 1.3.0 and 43 tools.

## Channel matrix

| Mode | Transport | Fallback | Notes |
| --- | --- | --- | --- |
| `auto` (default) | CDP when connected, otherwise the extension | Only when the CDP route is Unsupported | The extension remains the zero-setup path |
| `cdp` | Direct browser-level CDP only | None | Serves all 33 browser-facing tools, including the former extension-only eight |
| `extension` | Extension only | None | Serves 25 browser-facing tools; the 8 CDP-only tools fail with a typed error |

Select the mode with `--channel`, `CORVUS_CHANNEL` or the `browser_channel` tool. `--cdp-endpoint` takes the full loopback `ws://` or `wss://` browser URL from `/json/version`; `--no-cdp` removes the CDP path. The extension options page accepts `auto` or an explicit `http://127.0.0.1:<port>` discovery endpoint.

CDP is host-loopback only and unauthenticated. A browser-level endpoint can control every profile in that browser instance; never expose 9222, 9223 or 9333. See [07-cdp.md](../07-cdp.md) for launch flags, snapshot references, tool schemas and troubleshooting.

## Install

### Windows

The release ZIP contains `install-windows.ps1`, `uninstall-windows.ps1` and the vendored `nssm.exe`. Open an elevated PowerShell in the extracted archive and run:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\install-windows.ps1
```

The default root is `%ProgramData%\Corvus`; load the unpacked extension from `%ProgramData%\Corvus\extension`. A legacy `%USERPROFILE%\.corvus` tree is moved under the new root unless `-KeepLegacyData` is set. See [04-install.md](../04-install.md).

### Linux x86_64

```bash
mkdir -p corvus-1.3.0-linux-x86_64
tar -xzf corvus-1.3.0-linux-x86_64.tar.gz -C corvus-1.3.0-linux-x86_64
cd corvus-1.3.0-linux-x86_64
sha256sum -c SHA256SUMS
sudo ./install-linux.sh
```

The installer needs root and a running systemd. It creates the `corvus` service user, installs under `/opt/corvus`, writes and starts the unit, and waits for `http://127.0.0.1:7331/health`. Load the extension from `/opt/corvus/extension`. See [05-deployment.md](../05-deployment.md).

### Docker

```bash
docker volume create corvus-data
docker build -t corvus:1.3.0 .
docker run -d --name corvus \
  -p 127.0.0.1:7330:7330 -p 127.0.0.1:7331:7331 \
  -v corvus-data:/data corvus:1.3.0
curl -fsS http://127.0.0.1:7331/health
```

The image runs as UID/GID 10001 with `/data` as its home and carries the extension at `/opt/corvus/extension`. It contains no browser and cannot reach browser loopback on the host, so use the extension channel or `--no-cdp` inside the container.

### Kubernetes

```bash
docker build -t corvus:1.3.0 .
kind load docker-image corvus:1.3.0   # or push to your registry
kubectl apply -k deploy/k8s
kubectl -n corvus port-forward svc/corvus 7330:7330 7331:7331
```

The Service is a ClusterIP. A browser extension cannot reach it directly; use the port-forward or an authenticated proxy that the operator provides. CDP is not reachable from a pod by default. See [deploy/k8s/README.md](../../deploy/k8s/README.md).

## Verify

```bash
curl -fsS http://127.0.0.1:7331/health     # status ok, version 1.3.0
curl -fsS http://127.0.0.1:7331/metrics   # Prometheus text
corvus doctor
```

An MCP `tools/list` request returns exactly 43 tools. Call `browser_channel` with no arguments to read the active mode, CDP connection and extension state, and `cdp_status` for the endpoint, browser, protocol version, target count, reconnect count and last error. A compact snapshot returns one text block; clients must `JSON.parse` `content[0].text`.

## Known limitations

- NFR-3 is not passed. The clean 72-hour soak was stopped at the client's request after about eight hours, and 1.3.0 is not 72-hour soak certified.
- Firefox remains unsupported (NFR-6 deviation unchanged). Supported browsers are Edge, Chrome and Brave (Chromium 120+).
- CDP is loopback-only and unauthenticated, and a browser-level endpoint can control every profile in that browser instance. Never expose 9222, 9223 or 9333.
- The shipped Docker image and Kubernetes manifests contain no browser and cannot reach browser loopback on the host. A sidecar browser is not supported out of the box; use the extension channel or `--no-cdp`.
- Forced `cdp` never falls back. If the endpoint is unavailable, browser-facing calls fail instead of moving to the extension.
- macOS has no packaged installer; Linux packaging is x86_64 only. The image is not published to a registry, and Kubernetes manifests are release-gate checks rather than a hosted deployment.
- Extension tab ids and CDP target ids remain different namespaces. `@eN` and `@c<backendNodeId>` references are channel-specific and cross-channel use returns typed `BAD_ARGS`; a full bridge is deferred.
- An explicitly configured extension CDP endpoint changed while the daemon is already connected may require a daemon restart to take effect. Auto-discovered endpoint changes are re-polled every 500 ms and reconnect automatically.
- No live 1.3.0 deployment is claimed. The development machine used for packaging continued to run the existing 1.0.0 service.

## Upgrade from 1.2.0

The recording schema remains version 1, so a 1.2.0 database opens in place; no migration is required.

- Windows: run the 1.3.0 installer with the same `-HomeDir`. The installer refreshes binaries and the extension and keeps `data/corvus.db`.
- Linux: replace the installed tree with the 1.3.0 archive and rerun `install-linux.sh`; keep `<root>/data` and `<root>/config`.
- Docker: rebuild or pull the 1.3.0 image and keep the named `/data` volume. Kubernetes: update the image tag in the deployment.
- Reload the extension after replacing its files. Existing daemon URL and CDP endpoint settings are kept. Run `corvus doctor`, check `/health`, and call `tools/list` to confirm 43 tools.

See [Upgrade in the install guide](../04-install.md) and [05-deployment.md](../05-deployment.md).
