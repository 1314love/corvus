# Corvus 1.7.0 Acceptance Report

## 1. Purpose and verdict

**PASS.** The frozen v1.7.0 62-tool rescope adds 18 tools across page, input, tabs, storage and diagnostics while keeping the existing 44 tools and their schemas byte-identical. Both channels, the 42-handler extension build, all new tool families, batch policy, guardrails, recording, protocol and packaging expectations were validated on the frozen tree. Three Medium findings and one High finding found during validation were fixed and retested; no High or Medium finding remains open. The High finding was an extension passive-masking leak: password input values reached `page_snapshot` JSON/compact, `page_find`, `page_forms` and `page_accessibility`; it was fixed and independently retested on both channels. One end-to-end evidence gap is disclosed in sections 7 and 13: the 32 MiB page_pdf cap was not reached through a live tool call because the headless browser terminated while rendering oversized random-canvas pages; the cap remains covered by the Rust rejection path and its unit test.

## 13. Limitations and scope

- The 32 MiB `page_pdf` cap was not reached end-to-end: oversized random-canvas pages crashed headless Chrome before `Page.printToPDF` returned. The unit test and code paths cover the rejection, but this is not a live-cap PASS.
- The guardrail host gate is an application-level navigation check, not a network sandbox. A public hostname that resolves to a private address is not blocked without DNS resolution, and DNS rebinding remains out of scope.
- `browser_eval` and `page_html` can expose page-reachable data even when content boundary wrapping is enabled. The boundary is a prompt-injection marker, not a data-loss-prevention control.
- Content boundary wrapping applies to compact `page_snapshot` text, `page_text.text` and `page_html.html`; JSON snapshots, `page_find` and console output are not wrapped.
- Screenshot and PDF pixels are neither redacted nor boundary-wrapped. Password inputs are masked in form/snapshot output, but a visible secret can still appear in an image or PDF.
- Passive password masking covers snapshot, find, forms, accessibility and their recorded results. `page_html` and `browser_eval` are explicit raw-extraction tools and can still return a password value from the page. A caller-supplied search query is recorded in `page_find` arguments even when the result is empty; this is input provenance, not page-derived leakage.
- `redact_secrets` currently covers the `browser_cookies` result and the new cookie/storage recording shapes; other page data is unaffected.
- Read-only policy enforcement depends on tool metadata. Screenshots and PDFs are read-only and intentionally allowed under `read_only`; use `deny_tools` to block them.
- Policy is loaded once at startup. Changing the policy file requires a daemon restart.
- Authentication state is in memory. A restart recreates the bootstrap account and invalidates refresh tokens; pre-restart access tokens remain valid until expiry.
- CDP `page_accessibility` with a small `max_depth` can return only the root because meaningful nodes sit behind generic wrappers; this is contract-compliant but coarse.
- CDP `health.browser_count` and `connected_browsers` count the extension registry, not a CDP-connected browser, and CDP `cookie_set` omits `domain` as an empty string when the Domain attribute is absent while the extension reports the effective host. These are Low channel-consistency observations, not failures.
- Headless Chrome clamps `window_new` requested sizes to the existing 1280x800 window; this is an environment limitation, not a product contract failure.
- Tests used one Windows host, isolated ports and headless Chrome/Edge. No live browser, live daemon, NFR-3 72-hour soak or multi-host deployment was exercised. The tree is uncommitted; this report describes the working tree, not a published tag.
- No-policy coverage in this pass is the 49-check snapshot probe on each channel; the older auto-channel 29/40 legacy-tool harnesses were not rerun for the 62-tool rescope.
