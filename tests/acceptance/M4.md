# M4 acceptance: per-tab scheduling and MCP cancellation

This playbook is the human acceptance procedure for M4 wave 1. It is the source
of truth for the English text; [M4.zh.md](M4.zh.md) mirrors its sections and
commands.

## 1. Purpose

M4 wave 1 changes scheduling and cancellation. It adds no tool, no schema field
and no new success shape. The acceptance question is therefore narrow:

- Commands that target different tabs of the same browser run concurrently.
- Commands that target the same tab run strictly one at a time, in arrival
  order.
- A client can cancel an in-flight `tools/call` through the MCP streamable HTTP
  transport; the cancelled request returns JSON-RPC error `-32800` within two
  seconds, and later calls on the same MCP session still work.
- Cancelling an unknown or already-finished request id is a silent no-op.
- The frozen 32-tool surface and every input schema are byte-for-byte equivalent
  to the M3 snapshot.

Run the automated suite first. It proves the overlap and cancellation rules with
timestamps:

```bash
CARGO=/c/Users/Administrator/.cargo/bin/cargo.exe \
CORVUSD_BIN=./target/debug/corvusd.exe \
CORVUSD_ARGS="serve --ws-port 29330 --http-port 29331" \
CORVUS_DB="/tmp/corvus-m4-$(date +%s).db" \
CORVUS_MCP_URL=http://127.0.0.1:29331/mcp \
CORVUS_WS_URL=ws://127.0.0.1:29330 \
CORVUS_HEALTH_URL=http://127.0.0.1:29331/health \

```

The current suite ends with `RESULT: 135 passed, 0 failed, 0 skipped`. Copy the

Then perform the real-browser check below. It uses the same 32 tools against

## 2. Scope, scheduling rules and frozen tool names

The 32 frozen tools are unchanged:

```text
browser_click       browser_eval        browser_history     browser_hover
browser_list        browser_navigate    browser_press       browser_scroll
browser_select      browser_type        browser_wait        download_list
download_wait       logs_tail           metrics             net_capture
net_clear           net_intercept       net_log             page_find
page_html           page_snapshot       page_text           session_export
session_list        session_replay      session_steps       tab_close
tab_list            tab_new             tab_switch          upload_file
```

M4 adds these scheduling rules:

- The scheduler keys a gate by `browser_id` plus a tab scope. Tabs of different
  browsers never block each other.
- A command that accepts `tab_id` uses the exact `tab_id` value as its scope.
  If `tab_id` is omitted or empty, the scope is the browser's current active
  tab (`__active__`).
- Browser-level tools (`browser_list`, `tab_new`, `tab_close`, `tab_switch`,
  `download_list`, `download_wait`) use the browser scope (`__browser__`). A
  `net_intercept` or `net_clear` without `tab_id` also uses the browser scope.
- `browser_list`, `metrics`, `logs_tail` and the `session_*` tools are handled
  by the daemon locally and are never gated.
- Read-only tools such as `net_log` and `download_list` are not serialized with
  write work, but a same-tab call still waits for a running same-tab gate.

M4 also adds request cancellation:

- A client sends `notifications/cancelled` with `params.requestId` equal to the
  JSON-RPC id of the in-flight `tools/call`, using the same
  `Mcp-Session-Id`. The notification gets HTTP `202` and an empty body.
- The daemon removes the pending command, tells the extension to cancel it, and
  answers the original request with JSON-RPC `error.code = -32800` and message
  `request cancelled`. The response is an error object, never a tool result,
  and never has `result.isError`.
- A late daemon or extension result for that request is dropped. Cancelling an
  unknown id or an id that already completed is ignored with `202`, and later
  calls are unaffected.
- The cancelled step is recorded with `ok = false` and
  `error_code = "CANCELLED"` in `session_steps`.
- The extension uses an `AbortController` per command. `browser_wait` and
  `download_wait` abort cooperatively, `browser_eval` terminates execution, and
  `browser_navigate` stops loading. This does not change any success shape,
  schema or default timeout.

## 3. Prerequisites

- Windows with MSYS bash, Node.js 20 or newer, Rust toolchain, and the Edge
  browser with the unpacked extension.
- A local checkout at `D:/DSH/browser_bridege/corvus`.
- Ports 7430 (WebSocket), 7431 (HTTP/MCP) and 8808 (fixture) free. Do not use
  7330/7331: those belong to the installed Corvus service.
- The fixture page has two delayed elements: `#late` appears after 1200 ms and
  `#wait-status` changes text after 1200 ms. A fresh navigation restarts both

## 6. MCP session and helper

Set the endpoint and open one MCP session:

```bash
export MCP=http://127.0.0.1:7431/mcp
export PROTO=2025-06-18
curl -sS -D "$EVID/init.headers" -o "$EVID/init.json" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "MCP-Protocol-Version: $PROTO" \
  --data-raw '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"m4-acceptance","version":"1.0"}}}' \
  "$MCP"
export SESSION=$(awk 'BEGIN{IGNORECASE=1} /^mcp-session-id:/ {gsub(/\r/,""); print $2}' "$EVID/init.headers")
```

Send the initialized notification, then define the call helper. It always
records the JSON-RPC id, HTTP status and elapsed time:

```bash
curl -sS -o /dev/null -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "MCP-Protocol-Version: $PROTO" -H "Mcp-Session-Id: $SESSION" \
  --data-raw '{"jsonrpc":"2.0","method":"notifications/initialized"}' "$MCP"

post_call() {
  local id="$1" name="$2" args="$3" out="$4"
  curl -sS -o "$out" -w "$name id=$id http=%{http_code} time=%{time_total}\n" \
    -H "Content-Type: application/json" \
    -H "Accept: application/json, text/event-stream" \
    -H "MCP-Protocol-Version: $PROTO" \
    -H "Mcp-Session-Id: $SESSION" \
    --data-raw "{\"jsonrpc\":\"2.0\",\"id\":$id,\"method\":\"tools/call\",\"params\":{\"name\":\"$name\",\"arguments\":$args}}" \
    "$MCP"
}
```

The helper takes a numeric JSON-RPC id, a tool name, an arguments object and an
output file. Ids used below are fixed so the evidence is comparable: 401/402
for parallel waits, 403/404 for same-tab waits, 501/502 for cancellation, and
601/602 for the no-op check.

## 7. Baseline: 32 tools, own tab and first calls

Expected: exactly 32 names and `schema snapshot matches 32 tools`. Create two QA
tabs. Do not use a client tab:

```bash
post_call 101 tab_list '{}' "$EVID/tabs-before.json"

export BROWSER_ID=$(node -e 'console.log(require(process.argv[1]).result.structuredContent.browsers[0].browser_id)' "$EVID/browsers.json")
```

## 8. Two tabs run in parallel

Re-navigate both QA tabs to restart the `#late` timer, then issue both waits
before either can finish:

```bash
post_call 201 browser_navigate "{\"tab_id\":\"$QA_TAB_A\",\"url\":\"http://127.0.0.1:8808/m2\"}" "$EVID/nav-a.json"
post_call 202 browser_navigate "{\"tab_id\":\"$QA_TAB_B\",\"url\":\"http://127.0.0.1:8808/m2\"}" "$EVID/nav-b.json"
START=$(date +%s%3N)
post_call 401 browser_wait "{\"browser_id\":\"$BROWSER_ID\",\"tab_id\":\"$QA_TAB_A\",\"selector\":\"#late\",\"timeout_ms\":5000}" "$EVID/wait-401.json" &
P401=$!
post_call 402 browser_wait "{\"browser_id\":\"$BROWSER_ID\",\"tab_id\":\"$QA_TAB_B\",\"selector\":\"#late\",\"timeout_ms\":5000}" "$EVID/wait-402.json" &
P402=$!
wait $P401 $P402
END=$(date +%s%3N)
echo "wall_ms=$((END-START))"
```

Both calls must return `isError` absent or false, and each should report
`matched: true`. The wall time must be closer to one 1200 ms wait than to two:
less than 2500 ms on a healthy machine. If either call returns immediately,
navigate and repeat; a previous navigation may already have revealed `#late`.
The automated mock run proves the same rule with a 450 ms delay and a measured
wall of 481 ms.

Optional timestamp check: record `START` before the first call, then read
`session_steps` after both return and compare the two `browser_wait` steps'
`ts + duration_ms` values. Their intervals must overlap.

## 9. The same tab stays serialized

Use one tab only. Re-navigate to restart the timer, then send two waits to
`QA_TAB_A` at once:

```bash
post_call 203 browser_navigate "{\"tab_id\":\"$QA_TAB_A\",\"url\":\"http://127.0.0.1:8808/m2\"}" "$EVID/nav-serial.json"
START=$(date +%s%3N)
post_call 403 browser_wait "{\"tab_id\":\"$QA_TAB_A\",\"selector\":\"#late\",\"timeout_ms\":5000}" "$EVID/wait-403.json" &
P403=$!
post_call 404 browser_wait "{\"tab_id\":\"$QA_TAB_A\",\"selector\":\"#late\",\"timeout_ms\":5000}" "$EVID/wait-404.json" &
P404=$!
wait $P403 $P404
END=$(date +%s%3N)
echo "wall_ms=$((END-START))"
```

The second command must not start until the first has returned. The first wait
blocks for about 1200 ms; the second then sees `#late` already present and
returns quickly. Wall time around one wait is therefore expected, but the proof
is ordering, not duration. Read the recorded steps and verify the intervals do
not overlap:

```bash
post_call 204 session_steps "{\"session_id\":\"$SESSION\",\"limit\":30}" "$EVID/session-steps-serial.json"
QA_TAB="$QA_TAB_A" node -e '
const r = require(process.argv[1]);
const steps = r.result.structuredContent.steps.filter(
  (s) => s.tool === "browser_wait" && s.tab_id === process.env.QA_TAB
);
if (steps.length < 2) throw new Error("need two browser_wait steps, got " + steps.length);
const [a, b] = steps.slice(-2);
if (a.ts + a.duration_ms > b.ts) throw new Error("same-tab waits overlapped");
console.log("serial gap_ms=" + (b.ts - (a.ts + a.duration_ms)));
' "$EVID/session-steps-serial.json"
```

Expected: `serial gap_ms` is zero or positive. A negative value, or any overlap,
fails M4. The automated run records the same-tab options 461 ms apart in the
mock timing log, with the second start after the first end.

## 10. Cancel an in-flight wait through MCP

Start a long wait in the background, let it reach the extension, then send the
cancellation notification on the same MCP session:

```bash
post_call 501 browser_wait "{\"tab_id\":\"$QA_TAB_A\",\"selector\":\"#never\",\"timeout_ms\":30000}" "$EVID/cancel-wait.json" &
WAIT_PID=$!
sleep 0.3
CANCEL_START=$(date +%s%3N)
CANCEL_HTTP=$(curl -sS -D "$EVID/cancel.headers" -o /dev/null -w '%{http_code}' \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "MCP-Protocol-Version: $PROTO" -H "Mcp-Session-Id: $SESSION" \
  --data-raw '{"jsonrpc":"2.0","method":"notifications/cancelled","params":{"requestId":501,"reason":"qa m4 acceptance"}}' \
  "$MCP")
echo "cancel_http=$CANCEL_HTTP"
wait $WAIT_PID
SECOND=$(date +%s%3N)
echo "first_ms=$((SECOND-CANCEL_START))"
node -e '
const r = require(process.argv[1]);
if (!r.error || r.error.code !== -32800) throw new Error("expected -32800, got " + JSON.stringify(r));
if (r.result) throw new Error("cancelled call returned a tool result");
console.log("cancel_code=" + r.error.code + " message=" + r.error.message);
' "$EVID/cancel-wait.json"
```

Expected: `cancel_http=202`, a JSON-RPC error with code `-32800` and message
`request cancelled`, `first_ms` well under 2000, and no `result` key. The
automated run measured 56 ms from notification to the error response, with the
HTTP cancel itself returning 202 in 49 ms.

Then prove the same MCP session still works:

```bash
post_call 502 page_text "{\"tab_id\":\"$QA_TAB_A\"}" "$EVID/cancel-followup.json"
node -e 'const r=require(process.argv[1]); if(r.error) throw new Error("follow-up failed: "+JSON.stringify(r.error)); console.log("follow-up text length="+r.result.structuredContent.text.length);' "$EVID/cancel-followup.json"
```

Expected: a normal tool result containing the fixture text. Cancellation must not
poison the session, the tab gate, or the browser connection.

## 11. Cancelled response shape and recorded state

The exact shape is:

```json
{
  "jsonrpc": "2.0",
  "id": 501,
  "error": {
    "code": -32800,
    "message": "request cancelled"
  }
}
```

HTTP status is 200 for this JSON-RPC error response, as for any other tool
error. It is not a `tools/call` result, has no `result.isError`, and has no
`result.structuredContent`. The cancellation notification itself has HTTP 202
and an empty body.

The cancelled call is still visible in the session record:

```bash
post_call 205 session_steps "{\"session_id\":\"$SESSION\",\"limit\":30}" "$EVID/session-steps-cancel.json"
node -e '
const r = require(process.argv[1]);
const s = r.result.structuredContent.steps.find((x) => x.seq && x.tool === "browser_wait" && x.error_code === "CANCELLED");
if (!s) throw new Error("no CANCELLED step recorded");
if (s.ok !== false) throw new Error("CANCELLED step must have ok=false");
console.log("cancelled seq=" + s.seq + " tab=" + s.tab_id);
' "$EVID/session-steps-cancel.json"
```

If the step is absent, check that the notification used the same
`Mcp-Session-Id` and the numeric id `501`, not a string.

## 12. Cancelling an unknown or finished id is a no-op

Run a short call to completion, then cancel its id and an id that never existed:

```bash
post_call 601 page_text "{\"tab_id\":\"$QA_TAB_A\"}" "$EVID/noop-first.json"
for id in 601 999999; do
  code=$(curl -sS -o /dev/null -w '%{http_code}' \
    -H "Content-Type: application/json" \
    -H "Accept: application/json, text/event-stream" \
    -H "MCP-Protocol-Version: $PROTO" -H "Mcp-Session-Id: $SESSION" \
    --data-raw "{\"jsonrpc\":\"2.0\",\"method\":\"notifications/cancelled\",\"params\":{\"requestId\":$id,\"reason\":\"qa no-op\"}}" \
    "$MCP")
  echo "cancel $id -> $code"
done
post_call 602 page_text "{\"tab_id\":\"$QA_TAB_A\"}" "$EVID/noop-second.json"
node -e 'const r=require(process.argv[1]); if(r.error) throw new Error("later call failed: "+JSON.stringify(r.error)); console.log("later call ok");' "$EVID/noop-second.json"
```

Expected: both cancel responses are `202`; both `page_text` calls succeed; no
new error appears in the session. Cancelling a completed or unknown id is
ignored by design, not reported to the client.

## 13. Negative and boundary matrix

| # | Case | Call | Expected |
|---|------|------|----------|
| 1 | Cancelled call | `browser_wait` id 501 with `#never` and `timeout_ms` 30000, then cancel 501 | JSON-RPC `-32800`, no tool result, under 2 s |
| 2 | Cancel already finished | `page_text` id 601, then cancel 601 | HTTP 202, no later error |
| 3 | Cancel unknown id | cancel 999999 | HTTP 202, ignored |
| 4 | Follow-up after cancellation | `page_text` id 502 on same session | Normal tool result |
| 5 | Same-tab ordering | two `browser_wait` calls on one tab | Second starts after first ends |
| 6 | Different-tab overlap | waits on two tabs | Intervals overlap and wall time is about one wait |
| 7 | Schema drift | `tools/list` vs M3 snapshot | 32 tools and no schema change |
| 8 | Wrong session for cancel | notification with another or missing session | Rejected or not applied; original call is not cancelled |
| 9 | Unknown tool name | `tools/call` name `not_a_tool` | `BAD_ARGS`; tool list unchanged |
| 10 | Cancellation after disconnect | close session, then cancel | No effect; reconnect still gets 32 tools |

Cases 8-10 are diagnostic. Case 8 is only meaningful if the daemon can be made
to accept a second session; do not create a second client session on the
production service. Cases 9 and 10 can be checked in any order after the main
flow.

## 15. Pass criteria

M4 passes when all of the following hold:

1. The automated suite ends with `RESULT: 135 passed, 0 failed, 0 skipped` on
   the current tree and isolated ports.
2. `tools/list` returns exactly 32 names and `schema-check` reports no drift.
3. The two different-tab waits both succeed and their recorded intervals
   overlap; measured wall time is close to one wait, not two (reference mock:
   481 ms with a 450 ms delay).
4. The two same-tab waits both succeed, the second starts at or after the first
   ends, and the recorded gap is non-negative (reference mock: 461 ms apart).
5. The cancelled wait returns JSON-RPC `-32800` with message
   `request cancelled` in under 2000 ms, and no tool result is returned.
6. A `page_text` call on the same MCP session succeeds immediately after the
   cancellation.
7. Cancelling a finished id and an unknown id both return 202 and do not affect
   the following call.
8. A cancelled step appears as `ok=false` with `error_code=CANCELLED` in
   `session_steps`.
9. No client tab is closed, no client navigation is changed, and the installed
   Windows service on 7330/7331 is untouched.

A hard failure is any schema change, a cancelled request returning a success
tool result, a same-tab overlap, or a cancellation that takes longer than two
seconds. Record the exact response body and the request id in the report.

## 16. Cleanup and troubleshooting

Close only the QA tabs you created and leave the previously active tab active:

```bash
post_call 210 tab_close "{\"tab_id\":\"$QA_TAB_B\"}" "$EVID/close-b.json"
post_call 211 tab_close "{\"tab_id\":\"$QA_TAB_A\"}" "$EVID/close-a.json"
post_call 212 tab_switch "{\"tab_id\":\"$PREV_TAB\"}" "$EVID/restore-tab.json"
kill $(cat "$EVID/fixture.pid") 2>/dev/null || true
```

Stop the daemon with Ctrl-C in its shell and delete the temporary database and
the WAL/SHM files under `/tmp/corvus-m4`. Do not stop the Windows Corvus
service. Do not delete the user's downloads.

Troubleshooting:

| Symptom | Likely cause | Action |
|---------|--------------|--------|
| No `-32800`, the original request later succeeds | The notification went to another session, used a string id, or the binary predates M4 | Check `Mcp-Session-Id`, send the numeric id, rebuild |
| Cancellation HTTP is 200, not 202 | A regular `tools/call` was sent instead of a notification | Remove `id` and use `notifications/cancelled` |
| Follow-up call is `TRANSPORT_DOWN` | The browser or extension disconnected during cancellation | Reconnect the extension and repeat only the failed check |
| Same-tab gap is negative | A stale daemon or extension is running | Stop the isolated daemon, rebuild, reload the extension |
| Different-tab wall time is about two waits | Both waits resolved to the same tab scope | Pass distinct explicit `tab_id` values and verify with `session_steps` |
| `schema-check` reports drift | The tree is not the frozen M4 build | Rebuild from the reviewed commit; do not edit the snapshot |
| `session_steps` has no `CANCELLED` step | The wait completed before the notification arrived | Use `#never` and `timeout_ms` 30000, and cancel promptly |
