## 3. Method

### 3.1 page_snapshot matrix

For each of the three committed fixtures, the script opened a tab with tab_new (250 ms settle), then called page_snapshot for:

- mode = interactive and full
- max_nodes = 300 and 700

That is 12 calls. The page_snapshot JSON size is Buffer.byteLength(JSON.stringify(result.structuredContent), utf8). The tab was closed after each fixture. node_count, element_count, text_count, ref_count, node_cap, and truncated were checked to ensure the page was loaded and the cap was not binding.

The compact projection consumes the current page_snapshot nodes in DOM order and emits the v1.3 line grammar:

    @ref role "name" [states] value="..." bbox=x,y,w,h
    # "text"

Element line rules used for the primary projection:

- ref is the current extension ref, for example @e1, @e2, @e3
- role falls back to tag if role is empty
- name is included only when non-empty
- states are emitted in the fixed order disabled, checked, mixed, focused, required, expanded, selected
- checked=mixed is emitted as mixed, not checked
- value is included only when non-empty
- bbox is omitted by default
- name is escaped and truncated to 120 characters
- value is escaped and truncated to 80 characters
- text is escaped and truncated to 240 characters

Text nodes use the current node.text and the line form # "text". The primary projection includes all current nodes. The current v1.2.0 interactive snapshot already contains text nodes (live-page interactive is 3 elements + 4 texts), so text lines are present in both modes. If v1.3 interactive mode ends up element-only, the element-only column in the variant table is the relevant lower bound.

The projected compact result uses the task-87 shape:

    {format:"compact", tab_id, url, title, viewport, mode, node_count, truncated, text}

The compact-result byte count is the UTF-8 size of JSON.stringify of that object, with no MCP wrapper.

Token estimates are byte counts divided by 4. No real tokenizer was used.

### 3.2 MCP click -> snapshot loop

After the matrix, the script opened live-page.html, took one initial interactive snapshot (not counted in the loop), then ran three iterations of:

1. browser_click with target "#go"
2. page_snapshot with mode interactive and max_nodes 300

For each iteration it recorded the HTTP request body bytes and response body bytes for both calls, plus the exact JSON.stringify sizes of both structured payloads. Framing is wire minus payload, where wire is the sum of the four HTTP body sizes and payload is the sum of the two structuredContent sizes. HTTP headers, TCP, and TLS are not included. The three iterations were byte-identical.

### 3.3 Envelope confirmation

A separate probe, inspect-snapshot3.mjs, opened live-page.html, called page_snapshot, and printed the result keys, content[0].text, structuredContent, and serialized result size. This is the source of the 1,717 B / 1,018 B / 3,124 B decomposition in section 5. It was not part of the matrix.

## 5. Results: MCP framing for a click -> snapshot loop

### 5.1 Pristine snapshot response composition

For live-page interactive at max_nodes 300:

| Component | Bytes |
|---|---:|
| structuredContent JSON | 1,018 |
| content[0].text (pretty-printed JSON of the same object) | 1,717 |
| serialized result (content + isError + structuredContent) | 3,124 |
| full HTTP response body | 3,158 |
| response / structured JSON | 3.10x |

The content text is not a compact tree. It is JSON.stringify of the structured object with two-space indentation, so it repeats the whole snapshot in a second representation. JSON string escaping of that pretty text plus the content and structuredContent keys accounts for the remaining 389 B above the 1,717 + 1,018 raw text and structured payloads.

This is the single largest cost in the current transport. The compact grammar reduces the structured payload, but the same dual text + structured serialization will multiply the compact result too unless v1.3 changes it.

### 5.2 Three loop iterations

All three iterations were identical.

| Step | Request B | Response B | Structured payload B | Response envelope B |
|---|---:|---:|---:|---:|
| browser_click #go | 132 | 941 | 308 | 633 |
| page_snapshot interactive 300 | 154 | 3,216 | 1,036 | 2,180 |
| loop total | 286 | 4,157 | 1,344 | 3,099 |

The snapshot structured payload after the click is 1,036 B, 18 B larger than the pristine 1,018 B because the input value changed from empty to the clicked value. The snapshot response is 3,216 B, which is 3.10x the 1,036 B payload.

Loop accounting:

- Wire: 4,443 B
- Structured payload: 1,344 B
- Framing: 3,099 B
- Framing share: 69.75% of wire
- Requests are only 286 B, or 6.44% of wire; almost all overhead is response-side MCP duplication and JSON-RPC framing.

The projected compact result for this page is 358 B. The current loop spends 4,443 B of wire for 1,344 B of structured payload. Even if v1.3 reduces the structured snapshot to roughly 358 B, the MCP wrapper and the duplicate text representation must be measured separately; the 82% payload reduction is not an 82% wire reduction.

Budget headroom under 30,000 B:

| Measurement | Headroom |
|---|---:|
| tools array 29,926 | 74 B |
| result 29,936 | 64 B |
| body id=2 29,970 | 30 B |
| body id=10 29,971 | 29 B |

The current average tool definition is 29,926 / 42 = 712.5 B. Browser_batch is the planned 43rd tool. Even a minimal tool definition cannot fit in 74 B, let alone 30 B. The v1.3 brief catalogue therefore cannot satisfy the 30,000 B ceiling by simply adding browser_batch; existing brief entries must shrink, metadata must move out of the default response, or the budget must be restated on a different measure.

The full-detail body is 35,551 B. This is opt-in and is not the default contract, but it is already above 35,000 B before browser_batch is added. Any final budget should state whether full detail is exempt and what its new expected size is.

## 7. Surprises and risks

1. The 42-tool brief catalogue is already at the ceiling. The stable tools array is 29,926 B; only 74 B remain. Adding browser_batch without shrinking existing definitions is not possible under 30,000 B.

2. MCP response duplication dominates the snapshot cost. A 1,018 B snapshot is a 3,158 B response because content[0].text is a 1,717 B pretty-printed copy and structuredContent repeats the same object. The click-loop response is 3,216 B for a 1,036 B payload.

3. The max_nodes 300 and 700 runs are identical. All three fixtures are small (7 to 32 nodes), so the cap and truncation behavior were not exercised. The per-node averages are based on small pages and may not hold at 300 or 3,000 nodes.

4. The compact result is not the compact text. Metadata adds 253 to 331 B per snapshot. On live-page the text is 98 B but the result is 358 B. If the target is wire size, the metadata must be counted.

5. The baseline uses extension refs such as @e1, @e2, @e3. v1.3 CDP refs are @c<backendNodeId>, which are longer. Compact lines over CDP will be larger than these extension-based projections for the same DOM unless refs are shortened. This baseline does not measure that channel.

6. tools/list body bytes vary with the JSON-RPC id, even though the result is identical. The stable measures are the tools array (29,926 B) and result (29,936 B). A body-only budget can flip by a byte or two depending on the client id.

## 8. Limitations

- This is a v1.2.0 baseline on the extension channel only. No CDP browser or CDP snapshot was used. The CDP ref form and CDP serialization are not measured.
- The fixtures are all below the 300-node cap. No truncation or max_nodes boundary behavior is covered.
- The compact projection is an offline implementation of the task-87 grammar, not the v1.3 product implementation. It assumes the current node list, current refs, and the stated escaping and truncation rules.
- Token counts are bytes/4 estimates, not tokenizer measurements. Actual model tokenization may differ, especially for punctuation-heavy compact lines.
- The matrix uses one Chrome profile and one deterministic run. The three click-loop iterations were byte-identical, which supports reproducibility, but the viewport values and any browser-layout changes can affect node counts and bytes.
- No HTTP headers, TCP, or TLS bytes are included. Wire means HTTP body bytes only.
- The main working tree is dirty with task-87 changes. The measurements come from the clean detached worktree at c0e7c51, not from the current working tree.
- User Edge CDP 9222 and the live daemon 7330/7331 were not probed, attached to, navigated, or commanded.

## 9. Implications for the v1.3 target

The observed baseline supports these target statements:

- Compact text is roughly 23.3 B per node weighted on these small pages. A naive linear projection is about 6.99 KB of text at 300 nodes and about 69.9 KB at 3,000 nodes. These are extrapolations, not measured caps.
- The compact result adds about 282 B of metadata on top of the text. A 300-node result projects to about 7.27 KB under the same linear assumption.
- The JSON baseline mean is 2,077 B for the current fixtures. The compact text mean is 365 B (82.4% smaller); the compact result mean is 646 B (68.9% smaller).
- The MCP wire cost is a separate budget. The current dual text + structuredContent response is about 3.1x the structured payload. If v1.3 retains that shape, the wire reduction will be much smaller than the payload reduction. The product target should state whether it is defined on compact text, compact result, or actual MCP response bytes, and acceptance should measure all three.
- The brief catalogue has no room for a 43rd tool at current sizes. The browser_batch work must either reduce existing brief entries, move detail out of the default response, or explicitly change the 30,000 B contract. A body-only budget must also fix the request id form.
