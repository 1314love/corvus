# M4 验收：按标签页调度与 MCP 取消

本手册是 M4 wave 1 的人工验收流程。英文原文以 [M4.md](M4.md) 为准，本文逐节镜像其章节与命令。

## 1. 目的

M4 wave 1 只改变调度与取消，不新增工具、不新增 schema 字段、不改变成功响应形状。因此验收问题很集中：

- 发往同一浏览器不同标签页的命令可以并发执行。
- 发往同一标签页的命令严格一次一个、按到达顺序执行。
- 客户端可以通过 MCP streamable HTTP 传输取消正在执行的 `tools/call`；被取消的请求必须在两秒内返回 JSON-RPC 错误 `-32800`，且同一个 MCP 会话上的后续调用仍然可用。
- 取消未知或已完成的请求 id 是静默 no-op。
- 冻结的 43 个工具及其全部输入 schema 与 v1.3.0 快照完全一致。

先跑自动化套件，它用时间戳证明并发与取消规则：

```bash
CARGO=/c/Users/Administrator/.cargo/bin/cargo.exe \
CORVUSD_BIN=./target/debug/corvusd.exe \
CORVUSD_ARGS="serve --ws-port 29330 --http-port 29331" \
CORVUS_DB="/tmp/corvus-m4-$(date +%s).db" \
CORVUS_MCP_URL=http://127.0.0.1:29331/mcp \
CORVUS_WS_URL=ws://127.0.0.1:29330 \
CORVUS_HEALTH_URL=http://127.0.0.1:29331/health \
bash tests/conformance/run.sh
```

当前套件最后一行是 `RESULT: 135 passed, 0 failed, 0 skipped`。请把这一行原样抄进报告。自动化运行使用 29330/29331 上的独立守护进程和临时数据库，绝不能触碰已安装的 Windows 服务 7330/7331。

然后执行下面的人工浏览器检查。它使用同样的 43 个工具驱动 Edge 和本地 fixture。人工运行使用它自己创建的 Edge 标签页 id；mock 套件使用自己的 tab-1/tab-2/tab-3 编号。

## 2. 范围、调度规则与冻结的工具名

43 个冻结工具不变：

```text
browser_click       browser_eval        browser_history     browser_hover
browser_list        browser_navigate    browser_press       browser_scroll
browser_select      browser_type        browser_wait        download_list
download_wait       logs_tail           metrics             net_capture
net_clear           net_intercept       net_log             page_find
page_html           page_snapshot       page_text           session_export
session_list        session_replay      session_steps       tab_close
tab_list            tab_new             tab_switch          upload_file
```

M4 增加以下调度规则：

- 调度键由 `browser_id` 与标签页作用域组成。不同浏览器的标签页互不阻塞。
- 接受 `tab_id` 的命令使用精确的 `tab_id` 值作为作用域；省略或传空时，作用域是该浏览器当前活动标签页（`__active__`）。
- 浏览器级工具（`browser_list`、`tab_new`、`tab_close`、`tab_switch`、`download_list`、`download_wait`）使用浏览器作用域（`__browser__`）。不带 `tab_id` 的 `net_intercept` 或 `net_clear` 也使用浏览器作用域。
- `browser_list`、`metrics`、`logs_tail` 和 `session_*` 由守护进程本地处理，不参与调度。
- `net_log`、`download_list` 等只读工具不与写操作串行，但同一标签页的调用仍会等待该标签页正在执行的调度任务。

M4 同时增加请求取消：

- 客户端发送 `notifications/cancelled`，`params.requestId` 等于正在执行的 `tools/call` 的 JSON-RPC id，并使用同一个 `Mcp-Session-Id`。通知返回 HTTP `202` 和空响应体。
- 守护进程立即移除待处理命令，通知扩展取消，并给原请求返回 JSON-RPC `error.code = -32800`、消息 `request cancelled`。该响应是错误对象，绝不是工具结果，也不含 `result.isError`。
- 取消后迟到的守护进程或扩展结果会被丢弃。取消未知 id 或已完成的 id 会被忽略并返回 `202`，后续调用不受影响。
- 被取消的步骤记录为 `ok = false`、`error_code = "CANCELLED"`，可在 `session_steps` 中查看。
- 扩展为每个命令维护 `AbortController`。`browser_wait` 与 `download_wait` 协作式中止，`browser_eval` 终止执行，`browser_navigate` 停止加载。成功响应、schema 与默认超时均不变。

## 3. 前置条件

- Windows、MSYS bash、Node.js 20 或更高、Rust 工具链，以及已加载解包扩展的 Edge。
- 本地检出位于 `D:/DSH/browser_bridege/corvus`。
- 端口 7430（WebSocket）、7431（HTTP/MCP）、8808（fixture）空闲。不要使用 7330/7331：它们属于已安装的 Corvus 服务。
- fixture 页面有两个延迟元素：`#late` 在 1200 ms 后出现，`#wait-status` 在 1200 ms 后改变文本。重新导航会重置这两个计时器。

## 6. MCP 会话与辅助函数

设置端点并建立一个 MCP 会话：

```bash
export MCP=http://127.0.0.1:7431/mcp
export PROTO=2025-06-18
curl -sS -D "$EVID/init.headers" -o "$EVID/init.json" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "MCP-Protocol-Version: $PROTO" \
  --data-raw '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"m4-acceptance","version":"1.0"}}}' \
  "$MCP"
export SESSION=$(awk 'BEGIN{IGNORECASE=1} /^mcp-session-id:/ {gsub(/\r/,""); print $2}' "$EVID/init.headers")
```

发送 initialized 通知，然后定义调用辅助函数。它每次都记录 JSON-RPC id、HTTP 状态和耗时：

```bash
curl -sS -o /dev/null -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "MCP-Protocol-Version: $PROTO" -H "Mcp-Session-Id: $SESSION" \
  --data-raw '{"jsonrpc":"2.0","method":"notifications/initialized"}' "$MCP"

post_call() {
  local id="$1" name="$2" args="$3" out="$4"
  curl -sS -o "$out" -w "$name id=$id http=%{http_code} time=%{time_total}\n" \
    -H "Content-Type: application/json" \
    -H "Accept: application/json, text/event-stream" \
    -H "MCP-Protocol-Version: $PROTO" \
    -H "Mcp-Session-Id: $SESSION" \
    --data-raw "{\"jsonrpc\":\"2.0\",\"id\":$id,\"method\":\"tools/call\",\"params\":{\"name\":\"$name\",\"arguments\":$args}}" \
    "$MCP"
}
```

辅助函数接受数值 JSON-RPC id、工具名、参数对象和输出文件。下文固定使用这些 id，便于比较证据：401/402 用于双标签页并发，403/404 用于同标签页串行，501/502 用于取消，601/602 用于 no-op 检查。

## 7. 基线：43 个工具、自有标签页与首批调用

列出工具并与 v1.3.0 快照比较 schema：

```bash
curl -sS -o "$EVID/tools.json" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "MCP-Protocol-Version: $PROTO" -H "Mcp-Session-Id: $SESSION" \
  --data-raw '{"jsonrpc":"2.0","id":100,"method":"tools/list","params":{}}' "$MCP"
node -e 'const r=require(process.argv[1]); const t=r.result.tools; if(t.length!==43) throw new Error("expected 43 tools, got "+t.length); console.log(t.map(x=>x.name).sort().join(","));' "$EVID/tools.json"
node tests/conformance/m4_client.mjs schema-check "$EVID/tools.json" tests/conformance/schema-snapshot.v1.3.0.json
```

预期：恰好 43 个名字，且输出 `schema snapshot matches 43 tools`。先记录当前活动标签页，再创建两个 QA 标签页。不要使用客户端标签页：

```bash
post_call 101 tab_list '{}' "$EVID/tabs-before.json"
export PREV_TAB=$(node -e 'const t=JSON.parse(require(process.argv[1]).result.content[0].text).tabs.find(x=>x.active); if(!t) throw new Error("no active tab"); console.log(t.tab_id);' "$EVID/tabs-before.json")
post_call 102 tab_new '{"url":"http://127.0.0.1:8808/m2","active":true}' "$EVID/tab-a.json"
export QA_TAB_A=$(node -e 'console.log(JSON.parse(require(process.argv[1]).result.content[0].text).tab_id)' "$EVID/tab-a.json")
post_call 103 tab_new '{"url":"http://127.0.0.1:8808/m2","active":true}' "$EVID/tab-b.json"
export QA_TAB_B=$(node -e 'console.log(JSON.parse(require(process.argv[1]).result.content[0].text).tab_id)' "$EVID/tab-b.json")
post_call 104 browser_list '{}' "$EVID/browsers.json"
export BROWSER_ID=$(node -e 'console.log(JSON.parse(require(process.argv[1]).result.content[0].text).browsers[0].browser_id)' "$EVID/browsers.json")
echo "previous $PREV_TAB tabs $QA_TAB_A $QA_TAB_B browser $BROWSER_ID"
```

两个标签页都加载 `http://127.0.0.1:8808/m2`，标题为 `Corvus M2 Page`。保留这两个 id 供第 8、9 节使用。`QA_TAB_A` 是并发标签页，`QA_TAB_B` 是双标签页并发的第二个标签页。自动化套件后来创建的第三个标签页是 `tab-3`；该编号只属于 mock，不是人工契约的一部分。

## 8. 两个标签页并发

重新导航两个 QA 标签页以重置 `#late` 计时器，然后在任一等待结束前发出两个调用：

```bash
post_call 201 browser_navigate "{\"tab_id\":\"$QA_TAB_A\",\"url\":\"http://127.0.0.1:8808/m2\"}" "$EVID/nav-a.json"
post_call 202 browser_navigate "{\"tab_id\":\"$QA_TAB_B\",\"url\":\"http://127.0.0.1:8808/m2\"}" "$EVID/nav-b.json"
START=$(date +%s%3N)
post_call 401 browser_wait "{\"browser_id\":\"$BROWSER_ID\",\"tab_id\":\"$QA_TAB_A\",\"selector\":\"#late\",\"timeout_ms\":5000}" "$EVID/wait-401.json" &
P401=$!
post_call 402 browser_wait "{\"browser_id\":\"$BROWSER_ID\",\"tab_id\":\"$QA_TAB_B\",\"selector\":\"#late\",\"timeout_ms\":5000}" "$EVID/wait-402.json" &
P402=$!
wait $P401 $P402
END=$(date +%s%3N)
echo "wall_ms=$((END-START))"
```

两个调用都必须返回 `isError` 缺失或 false，且各自应报告 `matched: true`。总墙钟时间应接近一次 1200 ms 等待而不是两次：健康机器上小于 2500 ms。如果任一调用立即返回，请重新导航后再试；之前的导航可能已经让 `#late` 出现。自动化 mock 运行用 450 ms 延迟证明了同一规则，测得墙钟 481 ms。

可选时间戳检查：在第一个调用前记录 `START`，两个调用返回后读取 `session_steps`，比较两个 `browser_wait` 步骤的 `ts + duration_ms`，两个区间必须重叠。

## 9. 同一标签页保持串行

只使用一个标签页。重新导航以重置计时器，然后同时向 `QA_TAB_A` 发送两个等待：

```bash
post_call 203 browser_navigate "{\"tab_id\":\"$QA_TAB_A\",\"url\":\"http://127.0.0.1:8808/m2\"}" "$EVID/nav-serial.json"
START=$(date +%s%3N)
post_call 403 browser_wait "{\"tab_id\":\"$QA_TAB_A\",\"selector\":\"#late\",\"timeout_ms\":5000}" "$EVID/wait-403.json" &
P403=$!
post_call 404 browser_wait "{\"tab_id\":\"$QA_TAB_A\",\"selector\":\"#late\",\"timeout_ms\":5000}" "$EVID/wait-404.json" &
P404=$!
wait $P403 $P404
END=$(date +%s%3N)
echo "wall_ms=$((END-START))"
```

第二个命令在第一个返回前不得开始。第一次等待阻塞约 1200 ms；第二次随后看到 `#late` 已存在，会很快返回。因此墙钟接近一次等待是正常的，真正的证据是顺序。读取记录步骤并确认区间不重叠：

```bash
post_call 204 session_steps "{\"session_id\":\"$SESSION\",\"limit\":30}" "$EVID/session-steps-serial.json"
QA_TAB="$QA_TAB_A" node -e '
const r = require(process.argv[1]);
const steps = JSON.parse(r.result.content[0].text).steps.filter(
  (s) => s.tool === "browser_wait" && s.tab_id === process.env.QA_TAB
);
if (steps.length < 2) throw new Error("need two browser_wait steps, got " + steps.length);
const [a, b] = steps.slice(-2);
if (a.ts + a.duration_ms > b.ts) throw new Error("same-tab waits overlapped");
console.log("serial gap_ms=" + (b.ts - (a.ts + a.duration_ms)));
' "$EVID/session-steps-serial.json"
```

预期：`serial gap_ms` 大于或等于 0。负值或任何重叠都判 M4 失败。自动化运行在 mock 时间日志中记录到同标签页两次启动相隔 461 ms，第二次开始于第一次结束之后。

## 10. 通过 MCP 取消正在执行的等待

在后台启动一个长等待，等它到达扩展后，在同一个 MCP 会话上发送取消通知：

```bash
post_call 501 browser_wait "{\"tab_id\":\"$QA_TAB_A\",\"selector\":\"#never\",\"timeout_ms\":30000}" "$EVID/cancel-wait.json" &
WAIT_PID=$!
sleep 0.3
CANCEL_START=$(date +%s%3N)
CANCEL_HTTP=$(curl -sS -D "$EVID/cancel.headers" -o /dev/null -w '%{http_code}' \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "MCP-Protocol-Version: $PROTO" -H "Mcp-Session-Id: $SESSION" \
  --data-raw '{"jsonrpc":"2.0","method":"notifications/cancelled","params":{"requestId":501,"reason":"qa m4 acceptance"}}' \
  "$MCP")
echo "cancel_http=$CANCEL_HTTP"
wait $WAIT_PID
SECOND=$(date +%s%3N)
echo "first_ms=$((SECOND-CANCEL_START))"
node -e '
const r = require(process.argv[1]);
if (!r.error || r.error.code !== -32800) throw new Error("expected -32800, got " + JSON.stringify(r));
if (r.result) throw new Error("cancelled call returned a tool result");
console.log("cancel_code=" + r.error.code + " message=" + r.error.message);
' "$EVID/cancel-wait.json"
```

预期：`cancel_http=202`，JSON-RPC 错误码 `-32800`、消息 `request cancelled`，`first_ms` 远小于 2000，且没有 `result` 字段。自动化运行从发送通知到收到错误响应测得 56 ms，HTTP 取消本身在 49 ms 内返回 202。

然后证明同一个 MCP 会话仍然可用：

```bash
post_call 502 page_text "{\"tab_id\":\"$QA_TAB_A\"}" "$EVID/cancel-followup.json"
node -e 'const r=require(process.argv[1]); if(r.error) throw new Error("follow-up failed: "+JSON.stringify(r.error)); console.log("follow-up text length="+JSON.parse(r.result.content[0].text).text.length);' "$EVID/cancel-followup.json"
```

预期：正常工具结果，包含 fixture 文本。取消不得污染会话、标签页调度或浏览器连接。

## 11. 取消响应形状与记录状态

精确形状为：

```json
{
  "jsonrpc": "2.0",
  "id": 501,
  "error": {
    "code": -32800,
    "message": "request cancelled"
  }
}
```

这个 JSON-RPC 错误响应的 HTTP 状态是 200，与其他工具错误一致。它不是 `tools/call` 结果，没有 `result.isError`，也没有可解析的 `result.content[0].text`。取消通知本身返回 HTTP 202 和空响应体。

被取消的调用仍会出现在会话记录中：

```bash
post_call 205 session_steps "{\"session_id\":\"$SESSION\",\"limit\":30}" "$EVID/session-steps-cancel.json"
node -e '
const r = require(process.argv[1]);
const s = JSON.parse(r.result.content[0].text).steps.find((x) => x.seq && x.tool === "browser_wait" && x.error_code === "CANCELLED");
if (!s) throw new Error("no CANCELLED step recorded");
if (s.ok !== false) throw new Error("CANCELLED step must have ok=false");
console.log("cancelled seq=" + s.seq + " tab=" + s.tab_id);
' "$EVID/session-steps-cancel.json"
```

如果找不到该步骤，请检查通知是否使用了同一个 `Mcp-Session-Id` 和数值 id `501`（不是字符串）。

## 12. 取消未知或已完成的 id 是 no-op

先让一个短调用完成，再取消它的 id 和一个从未存在的 id：

```bash
post_call 601 page_text "{\"tab_id\":\"$QA_TAB_A\"}" "$EVID/noop-first.json"
for id in 601 999999; do
  code=$(curl -sS -o /dev/null -w '%{http_code}' \
    -H "Content-Type: application/json" \
    -H "Accept: application/json, text/event-stream" \
    -H "MCP-Protocol-Version: $PROTO" -H "Mcp-Session-Id: $SESSION" \
    --data-raw "{\"jsonrpc\":\"2.0\",\"method\":\"notifications/cancelled\",\"params\":{\"requestId\":$id,\"reason\":\"qa no-op\"}}" \
    "$MCP")
  echo "cancel $id -> $code"
done
post_call 602 page_text "{\"tab_id\":\"$QA_TAB_A\"}" "$EVID/noop-second.json"
node -e 'const r=require(process.argv[1]); if(r.error) throw new Error("later call failed: "+JSON.stringify(r.error)); console.log("later call ok");' "$EVID/noop-second.json"
```

预期：两次取消都返回 `202`；两次 `page_text` 都成功；会话中不新增错误。按设计，取消已完成或未知 id 会被静默忽略，不会报告给客户端。

## 13. 负向与边界矩阵

| # | 场景 | 调用 | 预期 |
|---|------|------|------|
| 1 | 取消执行中的调用 | `browser_wait` id 501，`#never`，`timeout_ms` 30000，然后取消 501 | JSON-RPC `-32800`，无工具结果，2 秒内 |
| 2 | 取消已完成调用 | `page_text` id 601，然后取消 601 | HTTP 202，后续无错误 |
| 3 | 取消未知 id | 取消 999999 | HTTP 202，忽略 |
| 4 | 取消后继续调用 | 同一会话 `page_text` id 502 | 正常工具结果 |
| 5 | 同标签页顺序 | 同一标签页两个 `browser_wait` | 第二次在第一次结束后开始 |
| 6 | 不同标签页并发 | 两个标签页的等待 | 区间重叠，墙钟约为一次等待 |
| 7 | schema 漂移 | `tools/list` 对比 v1.3.0 快照 | 43 个工具且 schema 无变化 |
| 8 | 取消时用错会话 | 使用另一个或缺失的会话发送通知 | 拒绝或不生效；原调用不被取消 |
| 9 | 未知工具名 | `tools/call` 名称 `not_a_tool` | `BAD_ARGS`；工具列表不变 |
| 10 | 断开后取消 | 关闭会话后取消 | 无影响；重连仍得到 43 个工具 |

第 8-10 项是诊断项。第 8 项只有在能创建第二个会话时才有意义；不要在生产服务上创建第二个客户端会话。第 9、10 项可在主流程后任意顺序检查。

## 14. 需要记录的证据

保存到 `$EVID`：

| 文件 | 内容 |
|------|------|
| `health.json` | 版本、协议、端口、已连接浏览器与 capabilities |

## 15. 通过标准

M4 通过需同时满足：

1. 自动化套件在当前代码树和独立端口上以 `RESULT: 135 passed, 0 failed, 0 skipped` 结束。
2. `tools/list` 恰好 43 个名字，`schema-check` 报告无漂移。
3. 不同标签页的两个等待都成功，记录区间重叠，墙钟接近一次等待而非两次（mock 参考：450 ms 延迟下 481 ms）。
4. 同标签页两个等待都成功，第二次在第一次结束后开始，记录间隔非负（mock 参考：相隔 461 ms）。
5. 被取消的等待在 2000 ms 内返回 JSON-RPC `-32800`、消息 `request cancelled`，且没有工具结果。
6. 取消后同一 MCP 会话上的 `page_text` 立即成功。
7. 取消已完成 id 与未知 id 都返回 202，且不影响后续调用。
8. 被取消的步骤在 `session_steps` 中显示 `ok=false`、`error_code=CANCELLED`。
9. 不关闭客户端标签页、不改变客户端导航，且不触碰 7330/7331 上已安装的 Windows 服务。

硬失败包括：任何 schema 变化；被取消请求返回成功工具结果；同标签页重叠；取消超过两秒。请在报告中记录精确响应体与请求 id。

## 16. 清理与故障排查

只关闭自己创建的 QA 标签页，并恢复之前活动的标签页：

```bash
post_call 210 tab_close "{\"tab_id\":\"$QA_TAB_B\"}" "$EVID/close-b.json"
post_call 211 tab_close "{\"tab_id\":\"$QA_TAB_A\"}" "$EVID/close-a.json"
post_call 212 tab_switch "{\"tab_id\":\"$PREV_TAB\"}" "$EVID/restore-tab.json"
kill $(cat "$EVID/fixture.pid") 2>/dev/null || true
```

在启动它的 shell 中按 Ctrl-C 停止守护进程，删除 `/tmp/corvus-m4` 下的临时数据库及 WAL/SHM 文件。不要停止 Windows Corvus 服务，也不要删除用户下载的文件。

故障排查：

| 现象 | 可能原因 | 处理 |
|------|----------|------|
| 没有 `-32800`，原请求后来成功 | 通知发到了另一个会话、用了字符串 id，或二进制早于 M4 | 检查 `Mcp-Session-Id`，发送数值 id，重新构建 |
| 取消的 HTTP 是 200 而不是 202 | 发成了普通 `tools/call` 而不是通知 | 去掉 `id`，改用 `notifications/cancelled` |
| 后续调用返回 `TRANSPORT_DOWN` | 取消过程中浏览器或扩展断开 | 重连扩展，只重跑失败项 |
| 同标签页间隔为负 | 残留了旧守护进程或旧扩展 | 停止独立守护进程，重新构建并重载扩展 |
| 不同标签页墙钟约为两次等待 | 两个等待解析到了同一标签页作用域 | 传不同的显式 `tab_id`，并用 `session_steps` 核对 |
| `schema-check` 报告漂移 | 代码树不是冻结的 M4 构建 | 从评审过的提交重新构建，不要修改快照 |
| `session_steps` 中没有 `CANCELLED` 步骤 | 等待在通知到达前已完成 | 改用 `#never` 和 `timeout_ms` 30000，并及时取消 |
